This page explains two things: how to move around this hub, and what to check whenever a change on one page affects another.

How to move around

  • The left sidebar is split into categories, like "Strategic Planning" or "Evidence & Assessment."
  • Each category has a number, showing a suggested reading order. There's no need to follow it strictly - jump to whatever needs work right now.
  • Every document in a category is always visible. Nothing needs to be clicked open first.
  • Hovering over a category or document name pops up a short note on what's inside.
  • Each document has a colored dot. Green means finished and confirmed. Amber means drafted, but still needs sign-off. Grey means it hasn't been written yet.
  • Underlined text inside a document is a real link. Clicking it jumps straight to that document.
  • "Version history," at the bottom of the sidebar, lists every change made to the hub.

A structural limit worth knowing

This hub is a single file, not a smart system. It can't notice on its own when a change in one document should also change another.

The fix is a standing habit: whenever a document changes, check its row in the table below. Fix what needs fixing, in the same sitting.

How the Playbook is organized

Partnership SOP v1.0 is the main rulebook. It covers how partners join, stay engaged, get grouped, and get help when something goes wrong.

A few documents stay separate on purpose:

  • The Communication Template Library holds ready-to-use scripts, not rules.
  • The Journey Map and Segmentation Framework hold research and analysis. They feed into the SOP. They are not the SOP itself.
  • The technical documents are written for developers, not for partners or Sarthy staff.

For why the Playbook is structured this way, or what it used to look like, see Design History & Decisions.

Keeping the dependency table current

  • Whenever something in the left column of the table below changes, the right column needs checking too. Fix what needs fixing, or confirm nothing needed to change.
  • Every structural change gets a note in Version History.
  • Any new connection between documents that isn't in the table yet gets added.

Flagging changes made outside this process

  • Any change made without going through this table should still be logged in Version History, so the table above stays accurate.
  • An amber or grey dot is a reminder that something else in the hub might still be waiting on it.
