A simple working tool for the Lead and Associate to actually run day-to-day operations on, until the real platform matures enough to handle it. Built directly on the Data Dictionary's field definitions - not a separate, invented structure.

What this replaces

The old Growth Partnerships tracker - 16 tabs, inconsistent columns, different team members' shorthand scattered across years. This is one clean structure instead, using the fields already defined in the Data Dictionary.

Migrating existing records - bulk import, predefined format

Decided approach: a spreadsheet template with one row per existing partner, columns matching the Partner fields already defined in the Data Dictionary - built and populated manually, not automated. Tracked as an open action item on the Action Item Tracker.

No partner or lead should exist in more than one place - if it's not in these five tables, it isn't tracked. That's the entire point of replacing the old tracker.

The Associate's daily call queue

Not a separate table - a filtered view of the Partners table, ordered by the Segmentation Framework's combined status + giving_pattern table:

  1. status = At-Risk first - highest priority, most time-sensitive
  2. status = Dormant next, but only this week's batch - selected on a rotating weekly quota, so every dormant partner eventually gets called rather than the same few being picked repeatedly or the list being worked by feel
  3. status = Active, giving_pattern = Taker - medium-high touch, before they slide into At-Risk
  4. status = Active, giving_pattern = Balanced - standard monthly rotation
  5. status = Active, giving_pattern = Giver - lowest priority for calls, light touch, mostly automated messages from the Communication Template Library

Each call logged with: date, partner_id, outcome (reached / no answer / rescheduled), and a free-text note - this becomes the historical record the old tracker's scattered comment columns used to (badly) serve.

What this tool is not

It doesn't replace the eventual app - it's scaffolding for the gap between now and whenever the real platform can do this natively. When the Business Requirements Document's features actually exist in the live product, this tool gets retired, not maintained in parallel.

Where this actually lives

A lightweight spreadsheet or simple tool (e.g. Airtable) is enough - the point is the structure above, not the software. Building actual automation here isn't necessary yet; consistency of the five tables is what matters.
