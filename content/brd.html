This is the To-Be system - what the marketplace app should do, written from Partnership SOP v1.0's rules, not from what's already built. This is deliberately not scoped to today's Alpha build - it's the target state. Once there's real portal access, the existing app gets compared against this document for a proper gap analysis, module by module. Each section is now tagged MVP (needed for a real first launch) or Phase 2 (can come after) - a few sections split, where the basic version is MVP but full automation can wait.

1. Purpose and how to use this

Every requirement below traces back to a specific Partnership SOP v1.0 section - if the rule changes there, this document needs to change too (see the dependency map on the Start Here page). Anything still marked open in the SOP shows up here as an open requirement too - this document doesn't invent answers the SOP doesn't have yet.

2. Who uses the system

  • Referring partner - submits leads, tracks their own credit balance, requests withdrawals
  • Receiving partner - gets matched leads, acknowledges or declines them, updates progress toward conversion
  • Startup / lead - the actual prospect being referred; may need to confirm engagement at points where trust needs verifying (see Section 8 below)
  • Admin (Sarthy) - validates leads, confirms conversions, resolves disputes, reviews flagged accounts, manages the whole system's integrity

3. Onboarding and fees MVP

Source: Partnership SOP v1.0, Section 5

  • The system must support two programme types (India, International), each with its own fixed fee (₹999 + GST, or $49) and identical starting credit grant (999 credits)
  • The system must lock a partner's programme choice permanently at sign-up - no switching later
  • The system must support digital signature capture for the referral agreement as part of onboarding
  • The system must let admin record onboarding evaluation notes (service relevance, client diversity, professional standing, Giver/Taker read) against a partner's profile
  • The system must activate the credit wallet with 999 opening credits immediately on fee payment confirmation

4. The credit wallet MVP

Source: Partnership SOP v1.0, Section 6

  • The system must maintain a running credit ledger per partner - every add and deduction, with a timestamp and a reason (fee payment, lead received, conversion earned, withdrawal, top-up)
  • The system must distinguish between credits a partner paid for (never expire) and credits Sarthy issued as goodwill (expire 30 days from issue) - and must actually enforce that expiry automatically, not rely on manual tracking
  • The system must not cap total balance for now, consistent with Section 6
  • The system must display a partner's current balance clearly, including how much of it is expiring soon

5. Lead submission and connection flow MVP

Source: Partnership SOP v1.0, Section 7, folded in from the confirmed Connection Request Flow. This replaces the old two-path, self-service-acknowledgment model - the requirements below are the current, authoritative ones.

  • The system must let any of the 3 initiating parties - a referring partner (direction A), a startup (direction B), or a receiving partner (direction C) - submit a connection request with enough detail for admin to run its sanity check
  • The system must check every new submission against existing open requests and automatically flag likely duplicates at the point of upload, before it reaches admin - not after
  • The system must show a partner a list of existing open requests, to reduce accidental duplicate submissions
  • The system must let the initiating party cancel a request any time before it reaches Acknowledged
  • The system must track a lead through defined stages: Submitted → Introduced (immediate, visible to all relevant parties, faded/FYI-only) → Validated (admin's sanity check) → Acknowledged → In Progress → Converted / Rejected
  • The system must have admin - not the receiving partner directly - take consent from every required requested party before a request can reach Acknowledged: the receiving partner in all 3 directions, and the startup as well in directions A and C. Consent refusal at any point moves the request to Rejected, with no deduction ever having happened
  • The system must not auto-finalize or auto-close a request on any timer. There is no equivalent of the old 7-day acknowledgment window any more - a request can sit at Introduced or Validated indefinitely; it only changes state when admin actively approves it or a required party refuses consent
  • The system must deduct 999 credits from the receiving partner's wallet the moment admin approves (reaches Acknowledged) - not before, not after
  • The system must let the admin manually reverse a deduction in disputed cases, based on the merits, at any point after Acknowledged - see Section 11 below for the evidence mechanism
  • The system must flag any receiving partner with 4 or more consecutive consent refusals to admin for manual review
  • The system must allow a lead to be re-requested an unlimited number of times after a refusal
  • The system must show, not block, same-service-type overlap - flagging the receiving partner when a startup already has another open request or active engagement with a similar-type partner, rather than preventing the new request outright. Not yet answered: whether one request converting to Acknowledged should auto-close the startup's other open requests to similar-type partners - needs a decision before this is built, see the Connection Request Flow page
  • Resolved: every state-changing action on a lead - a status change, a consent decision, a conversion, a dispute update - must automatically email every party connected to that lead, plus admin. This is a blanket requirement across the system, not decided case by case
  • The system must let a startup browse the list of vetted partners and request one directly (direction B), without requiring a specific partner to have referred them first
  • The system must let a receiving partner browse the full startup list and propose a connection directly, with a business proposal (direction C)
  • The system must track which partner (if any) originally brought a given startup into Sarthy's ecosystem (originating_partner_id), separately from which partner the startup ultimately engages with - these can be different partners in any of the 3 directions
  • The system must route both the 999-credit lead-share reward and the 10% deal-closure referral fee to the originating partner, regardless of which of the 3 directions produced the eventual connection
  • The system must treat Sarthy itself as the originating partner when a startup signs up with no partner having brought them in - every reward mechanic that applies to a normal partner applies to Sarthy the same way in this case
  • Not yet scoped for build: a backend matchmaking layer, still in early direction only - see Partnership SOP v1.0, Section 7 for the current thinking. Needs its own design pass before it's a real requirement.

6. Conversion and disputes MVP

Source: Partnership SOP v1.0, Section 9

  • The system must support the same conversion standard for every service category - proof of first payment plus a digitally signed agreement, captured in-platform
  • The system must credit the referring partner 999 credits minus the 9% fee (about 909 net) the moment admin confirms conversion - see Section 7 below for the fee mechanic
  • The system must let a partner formally dispute a conversion decision within 14 days of it being made, in writing, through the platform
  • The system must notify admin immediately when a dispute is raised, with a target response time of 24 hours
  • The system must let a partner remaining unsatisfied after admin's response escalate a dispute directly to Sarthy leadership. Resolved: there's no fixed deal-value threshold. Every escalation must trigger an automatic notification to admin - an in-product popup, plus an automated email - the moment it happens. Admin then decides how to proceed, including whether to loop in Sarthy leadership, based on the specifics of the case.

7. Withdrawal and the credit wallet's money mechanics MVP

Source: Partnership SOP v1.0, Section 10

  • The system must treat membership as ongoing - no cycle-end event, no forced settlement date
  • The system must enforce a minimum reserve of 999 credits at all times - a partner cannot withdraw below that floor
  • The system must support quarterly withdrawal requests for anything above the reserve
  • The system must apply the 9% fee once, at the point credit transfers to a referring partner on conversion - not again at withdrawal, since it's already been taken at the source
  • The system must convert credits to real currency using the live exchange rate on the day of withdrawal, not the rate from sign-up. Resolved: the official source is a government-approved, publicly available real-time rate chart - specifically the RBI reference rate.
  • Resolved: the 9% facilitation fee applies to every partner, including those still under Partner 1.0-era agreements. Where an existing agreement doesn't support this, it needs to be amended - see the Action Item Tracker for the documentation task this creates.

8. Post-closure referral fee tracking MVP

Source: Partnership SOP v1.0, Section 20

  • The system must let a receiving partner record deal value and duration once a referred lead closes into a signed agreement
  • The system must notify Sarthy and the original referring partner when this happens
  • The system must apply a 12-month proration rule when deal_duration exceeds 12 months - the referral fee is calculated only on value invoiced during the first 12 months, not the full multi-year contract
  • The system must calculate the referring partner's entitlement as 10% of the applicable (prorated, if needed) value, then deduct Sarthy's 9% cut of that 10%, crediting the referring partner the remaining 91%
  • The system must treat a startup being referred to a different partner later as a completely separate deal, with its own independent 12-month entitlement clock - not linked to any prior engagement with a different partner
  • The system must accumulate this amount in the referring partner's account separately from their 999-point credit wallet - this is a different pool, on a different payout schedule
  • The system must pay out the accumulated referral-fee balance once annually, at financial year-end (March 31st)
  • The system must track a 1-year expiry from the lead's first engagement date, after which no further referral-fee entitlement accrues to the original referring partner on that relationship

9. Partner activity requirement (dormancy) MVP (tracking) / High priority (gamification)

Source: Partnership SOP v1.0, Section 21

  • The system must track the date of a partner's last shared lead
  • The system must automatically mark a partner dormant after 3 consecutive months with no lead shared
  • The system must remove a dormant partner from the public portal listing and block them from receiving new leads until they resume activity
  • Resolved: the system must send an automated reminder message to every dormant partner on a weekly basis, not a rotating subset - separate from the Associate's own manual call queue, which still works through dormant partners on a rotating weekly quota because of team bandwidth
  • Resolved: reactivation has no formal gatekeeping - a dormant partner who resumes activity (e.g. sends a lead) simply returns to Active (or At-Risk/Frozen if those conditions independently apply), picking up from their last state and next step
  • Resolved - high priority: gamification elements (leaderboards, streaks, recognition) to encourage consistent giving. This is to be designed and built alongside the rest of the MVP features, not deferred. The specific mechanics still need a real design pass.

10. Negative balances MVP

Source: Partnership SOP v1.0, Section 8

  • The system must allow a partner's balance to run negative down to -2,997 credits
  • The system must automatically freeze a partner's ability to receive new leads once their balance hits -2,997
  • The system must support a top-up payment (4x the entry fee - ₹3,996 or $196) that adds 3,996 credits back to a frozen wallet, bringing the balance from -2,997 to exactly +999
  • Resolved: a Frozen partner must still be able to submit/refer a lead to someone else - the freeze only blocks receiving. A referral from a Frozen partner must route to admin for an extra validation step before it's shown to the receiving partner

11. Trust and evidence - the dispute-reversal mechanism MVP - discretion confirmed, contact form still needs design

Source: Partnership SOP v1.0, Section 7

For disputed cases raised after Acknowledged, the system should reach out directly to the startup to confirm whether the receiving partner actually engaged with them, and use that as evidence for admin's manual reversal decision.

  • The system needs a way to contact the startup lead directly (a short form or message) and capture their confirmation or denial. The exact form this takes still needs a design pass.
  • Resolved: the startup's confirmation is not mandatory. It's one input among several the admin weighs, entirely at admin's discretion.
  • Resolved: if the startup doesn't respond either, that's also handled at admin's discretion. There's no fixed default favoring either partner.

12. Guardrails and admin tools MVP (basic) / Phase 2 (pattern detection)

Source: Partnership SOP v1.0, Section 13

  • The system must give admin visibility into referral patterns across the whole network, to spot suspicious coordination between just one or two partners
  • The system must flag partners with consistently low conversion rates for admin review
  • The system must support admin manually freezing or exiting a partner's account in cases of confirmed abuse
  • Resolved: the system must automatically restrict likely misuse of the browse-and-request feature, based on a defined rule set, rather than relying on admin's manual judgment alone. [Note: the specific rules still need to be written and filled in.]

13. Reporting Phase 2

Source: Partnership SOP v1.0, Section 19, Reporting Dashboard

  • The system must be able to report, at minimum monthly, on all 4 of Sarthy's scorecard categories - not just Match-Making. See the Reporting Dashboard for the exact measures and data sources for each.
  • The system must support recording written recommendations coming out of that reporting, and whether they were acted on
  • Not yet built anywhere: a startup-contact log (separate from the partner call queue) and a contact-date field on the Partner record - both needed before the "Supporting startups" and "Finding & signing partners" categories can actually report real numbers

14. Integration requirements MVP (payments, e-sign) / Phase 2 (automation)

Every one of these is implied by the rules above but never named as an actual technical dependency until now. Selection status tracked on the Action Item Tracker, not here - this section defines what needs to integrate, not which vendor.

  • A payment gateway - for collecting the ₹999/$49 entry fee and processing withdrawal payouts. Selection pending.
  • A digital-signature provider - for the referral agreement (Section 3) and conversion confirmation (Section 6). Selection pending.
  • A notification channel (email and/or WhatsApp) - for every trigger in the Communication Template Library. Specific provider not yet chosen.
  • An exchange-rate data source - for converting credits to real currency at withdrawal (SOP Section 10). Resolved: the RBI reference rate, per SOP Section 10 - what's left here is picking/confirming the actual integration, not deciding which source counts as official.
  • An SSO provider - for the startup-facing self-service product (Section 5). Selection pending.

15. Non-functional requirements

A reasonable baseline, not a formal compliance commitment - can be revisited once real usage and Sarthy's own constraints are clearer.

  • The system must encrypt financial and personal data both at rest and in transit - this handles partner bank/payout details and startup contact information, not just operational data
  • The system should collect only the data fields already defined in the Data Dictionary - no speculative data collection beyond what a defined rule actually uses
  • No formal uptime commitment for now - reasonable best-effort availability is sufficient at this stage, not a contracted SLA

16. How each requirement gets verified

A general principle, plus the specific cases most likely to be interpreted differently by different developers without an explicit test:

  • Duplicate lead detection: submitting the same contact's details twice within the system should be caught and flagged before the second submission reaches admin - test by submitting an intentional duplicate and confirming it's blocked at upload, not after.
  • No auto-finalization: a request left untouched at Introduced or Validated should still be sitting there, unchanged, no matter how much time passes - test by leaving a request deliberately untouched for well beyond the old 7-day window and confirming nothing about its state or the receiving partner's wallet changes on its own.
  • Negative balance freeze: a partner whose balance reaches exactly -2,997 should be blocked from receiving further leads immediately - test by driving a test account to exactly that balance and confirming the block fires at -2,997, not -2,998 or later.
  • 12-month proration: a deal reported with a duration over 12 months should calculate the referral fee only on the portion attributable to the first 12 months - test with an 18-month deal and confirm months 13-18 don't affect the payout.
